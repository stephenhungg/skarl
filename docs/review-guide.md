# Skarl review guide

Skarl fills two seats for a human-data operator: **settlement accountant + AP clerk**. It connects evidence about a submitted demonstration to a payable, a buyer-signed policy approval and an observed settlement. Agents propose, the internal policy service approves eligible within-cap obligations, and the owning buyer reviews exceptions. This guide maps the implemented controls to official track requirements; it does not claim prize eligibility or a completed production service.

Official criteria were rechecked on **October 25, 2026** against [Cal Hacks Devpost](https://cal-hacks-13-0.devpost.com/), the original [Hyphenate brief](https://docs.google.com/document/d/1u4iN8R97ILY3kfHTPKC82zdutHrGx4ze5eCAP-J92w4/edit), [Coinbase brief](https://drive.google.com/file/d/12TnPLguduV3gh1zY_TJ176XmVDz2RGW9/view), [Atlassian brief](https://docs.google.com/document/d/12Y2Vamxbm9W_l2Eo4AM530R7HfNAYCXI-UI6F6Xnggw/edit) and [Hacker Guide](https://docs.google.com/document/d/1RQrueC9wm5u8uxtWSC2gadIchp05hVayhGUrIjxT9dE/edit). Sources describe requirements; the evidence below describes what Skarl has actually demonstrated.

## Reproduce locally

Use the pinned Node 22 line and pnpm version from [setup](setup.md):

```sh
pnpm install --frozen-lockfile
pnpm check
```

`pnpm check` runs typechecks, package/Convex/payment/web tests, documentation checks and a production build. It does not deploy, start inference, send money or establish sponsor integration. Fixtures and recorded/replayed results must retain those labels. Do not run a seed, scenario, upload, payment or cloud sync merely to review the repository; operator workflows are separately documented.

The track-specific commands below run isolated tests with synthetic provider/chain inputs unless otherwise stated. Run them from the repository root. The Forge integration has its own lockfile and separate checks.

## What the controls actually enforce

The happy path starts with the buyer setting an audited auto-pay rule and per-clip cap on the order. The internal-only [policy engine](../convex/policy.ts) is distinct from the proposing finance agent. It requires a bound completed accepting report, all rubric criteria supported, unanimous available accepting visual judges, a clear duplicate check, any issued liveness challenge passing, no instruction flag, valid consent and funded remaining quota before invoking acceptance. Policy approval then rechecks the accepted payable, verified wallet, exact stored terms, funded/reserved balances and buyer cap. A failed check becomes an exception for the owning buyer; the legacy controller path remains for compatibility. This is buyer-authorized automation, not a fresh human click on every payout or a claim that the AI approves itself.

[Acceptance and exception review](../convex/finance.ts) retain the hard gates: funded/open quota and frozen terms, verified original/source and consent, a verified contributor wallet, and no accepted exact/perceptual copy. The authorized owning buyer can record an evidence-bound decision and review a payment exception; this does not waive the hard source/licensing/duplicate/financial bindings. Verification-only evaluation media cannot become saleable or payable.

The [dashboard witness panel](../apps/web/features/dashboard/witnesses.tsx), [reconciliation page](../apps/web/features/dashboard/reconciliation.tsx) and [scenario lab with run confirmation](../apps/web/features/dashboard/scenarios.tsx) surface these records without granting new authority. The [witness receipt](../convex/witnessReceipt.ts) exposes missing, pending, agreeing and disagreeing evidence. **It is not an “all witnesses green” approval gate.** Sensors, client-computed detector/hand overlays, EAS availability and the Nessie comparison are advisory or separate observations. Quality scores are heuristics. An EAS commitment proves what was recorded, not that the recording or recommendation is correct.

Payment proposals cannot change stored recipients or amounts, and the proposing agent cannot approve. The buyer-signed deterministic policy or owning buyer’s exception review supplies stored approval; Workflow rechecks authority and bindings before dispatch. With `PAYOUT_EXECUTOR=cdp_agent`, the existing executor and independent CDP wallet cap guard sending. Legacy controller/browser-wallet execution remains available. A submitted hash is not settlement: exact network/token/sender/recipient/amount, confirmations, unique chain-log identity and journal posting establish the paid state. No deployed or successful auto-pay run is inferred from the new policy source.
