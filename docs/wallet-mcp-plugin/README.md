# Use Skarl from your agent

This directory contains a reusable [Skarl Wallet MCP plugin](skarl.md) for funding orders and purchasing verification evidence. It is a custom instruction file, not an installed or Coinbase-approved marketplace integration.

Start with the [Wallet MCP demo runbook](../wallet-mcp-demo.md): the approved demo is ONE operator-provisioned 1 USDC order paying the existing `skarl-finance-agent` wallet, with contributor auto-pay disabled. It can demonstrate funding without first collecting a licensed clip. Backend and web changes still need deployment before provisioning and the guarded flow can run. The recorded SDK/facilitator transfers prove those integrations; they do not prove a Wallet MCP purchase. Checking the already-funded v2 order is a no-charge read.

## Three steps

1. Connect [Coinbase Wallet MCP](https://docs.cdp.coinbase.com/coinbase-for-agents/wallet-mcp/references/install) to your agent. For Claude Code, run `claude mcp add --transport http --scope user base-mcp https://wallet-mcp.coinbase.com`. For Codex, run `codex mcp add base-mcp --url https://wallet-mcp.coinbase.com/`. Authorize the connection and have Base Sepolia test USDC in the connected wallet.
2. Give the agent [skarl.md](skarl.md), or copy it to `skills/base-mcp/plugins/skarl.md` in an existing Wallet MCP skill installation. Ask it to run Wallet MCP onboarding and read the plugin. No Skarl server credentials are needed. An HTTP-capable agent can perform creation and unsigned POST preflight; chat-only clients need a supported HTTP tool/host for those operations. A pasted GET response cannot replace a POST.
3. Ask “Fund operator-provided Skarl order ORDER_ID once with at most 1 USDC on Base Sepolia, paying skarl-finance-agent at 0x0A9EfDF66c58543538824906aE267B969Ed651c5 with contributor auto-pay disabled.” Obtain that ID from the deployment owner: after clean-main deployment, `payments:createWalletMcpDemo {}` idempotently provisions that same single order without signing or paying. The agent validates the stored payee, disabled rule, amount and funding commitment, then preserves the emitted `Idempotency-Key` and `X-Skarl-Funding-Terms` headers through actual Wallet MCP initiation. The human approves in Coinbase Wallet; the agent completes the same request ID and verifies seller/RPC confirmation. Never create another order or payment after an uncertain result.

For another buyer, public `POST /api/orders` remains an alternative with a fixed task and human-treasury default. It cannot choose the agent profile or an arbitrary recipient. Choose `autoPay` explicitly, use a stable creation `Idempotency-Key`, and retry the same key/body after a lost response. `{}` defaults auto-pay on, so disclose that before creation. No global treasury setting or existing order is changed by the single operator demo.

For evidence: “Buy Skarl sample sample-SUBMISSION_ID's evidence for at most 0.25 USDC.” The implemented endpoint charges `0.250000` USDC for an eligible accepted, delivered sample and returns the stored report plus five-minute media access after confirmed settlement. Evidence pays the separate `skarl-finance-agent` revenue account through `SKARL_EVIDENCE_PAYTO`; default public orders pay the human treasury; the single operator demo pays its frozen agent recipient as an order prepayment, not evidence revenue. The October 25, 03:12 PDT handoff recorded no eligible sample or live paid evidence sale; query actual availability rather than treating that dated inventory as current. Stop at `404` without paying. Search explicitly uses `network: "base-sepolia"`; an absent listing means indexing is unproven. No live Wallet MCP payment or successful Bazaar listing is claimed by these instructions alone. See [build status](../status.md) and the [evidence contract](../x402-bazaar.md).

## Optional repository coordinator

After the operator provides the single order ID, use `pnpm wallet:fund prepare ORDER_DOCUMENT_ID --max-payment-atomic 1000000 --expected-pay-to 0x0A9EfDF66c58543538824906aE267B969Ed651c5 --payer CONNECTED_WALLET_ADDRESS --state work/wallet-funding.json`. The [runbook](../wallet-mcp-demo.md#durable-handoff-from-the-repository) gives the exact `record`, `resume`, `begin-completion` and `status` sequence. The coordinator preflights terms and retains one request across interruptions; it does not invoke MCP, sign, approve or send. The connected agent calls the actual Wallet MCP tools and the human approves. Seller/RPC status checks and operator-recorded tool metadata are distinct evidence. The coordinator independently checks the versioned terms hash and requires its funding header; legacy callers may omit it. A stale-terms `409` stops for buyer review and reconciliation, never automatic reauthorization. Both web and Convex must expose/enforce the commitment before this guarded flow can run. This optional CLI does not change the plugin's HTTP routing or install Coinbase tools.

## Review and integration status

The plugin follows the [Coinbase plugin specification](https://docs.cdp.coinbase.com/coinbase-for-agents/wallet-mcp/references/plugin-spec) for frontmatter and section ordering. Its submission tools are the actual x402 approval tools, consistent with Coinbase's [Brickken x402 example](https://docs.cdp.coinbase.com/coinbase-for-agents/wallet-mcp/plugins/brickken), rather than a raw calldata conversion.

The repository does not include Coinbase's `plugin-review` skill; review here is a local structure/link check, not upstream certification. Shipping this file does not register a Bazaar listing or update Coinbase's `web_request` allowlist. See [deployment](../deployment.md) and [status](../status.md) for live evidence and remaining limitations.
